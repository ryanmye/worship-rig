## Claims checked

- **INTERFACE-CHANGE O-W3-1: as decided, additive, and safe on the audio thread.**
  - `VoicePool::fadeNote` makes one pass over the pool's capacity, allocates nothing and takes no lock. Its second
    `markKilled` is idempotent (`counts()` guard).
  - Decode and route are one `case` each in `graph.cpp` and `instrument_apply.cpp`. The T13 command gate's default
    branch covers `FadeNote`.
  - Deviation: DECISIONS says `float seconds`; the code uses `double`. That is harmless because `Command::f` is double.
- **Re-strike ordering.** `FadeNote` and the following `NoteOn` share a frame, and `Command::seq` keeps them FIFO.
  A pedaled entry can never share a channel and sounding note with a held key: the re-strike unpedals it first. So
  "fade every Held voice of note n" addresses exactly the voice JS addresses.
- **`release-pedalhold` does not prove the pedalHold fade: correct, but for a less obvious reason.**
  - The golden drops to digital silence at 5.4-5.8 s, which looks like the fade.
  - It is actually the end of `ep-rhodes/E4.mp3`: 3.16 s long, with a baked 0.4 s tail fade, started at 2.6 s.
  - The 5.4 s timer finds nothing, as claimed. I noted this in `t14.ids`.
- **`bend-tape` and the per-channel `DelayNodeKernel::process`.**
  - The new overload is the old loop with the channel loop moved outside. It is bounded, allocation-free and uses a
    stack array.
  - The structural claim is that Chromium runs one `DelayDSPKernel` per channel, and each kernel calls
    `CalculateSampleAccurateValues` itself. **I checked this from memory, not against the 157 source.** The bit-close
    result supports it.
- **Perform runs on the control thread only.** The quiet probe is called from `ReverbPool::quietTick`, a sink timer,
  so it is on the control thread too. Construction and destruction order is safe: `perf_` is built after the services
  and destroyed before them.
- **Ports checked line by line against audio.js** (noteOn, noteOff, sustain, pedalHold, mono, allNotesOff, fadeOutAll,
  quietFor, touch, wheels, swell, glide, bend, tape): no divergence on a parity path. Differences outside parity:
  - **Tape realtime lead.** Native is a fixed 20 ms; JS is `min(50 ms, baseLatency + 10 ms)`. The comment says the
    JS formula. Nit.
  - **`monoSwitch` legato.** It does not check that the current voice is still Held. JS requires
    `cur.voice.state === 'held'`. A voice stolen by the cap or the D4 limit therefore gets `LegatoTo` (a no-op), and
    the mono line stays silent until the next note. JS retriggers instead. Low; it needs a voice-state query, or a
    rule in `legatoTo` that a missing voice means noteOn.
- **Test counts.** `unit.perform` has 18 cases and `unit.wheels` had 8 (now 9 with F1's test), not 17 and 9. Trivial.

## Findings needing a change outside T14's files

### F1 (medium, T05 file `src/fx/delay_register.cpp`): the delay ignores the macro.wash feedback override

JS applies the wash override in three places:

- `Delay.applyAll`: commit, `pingpong`, `tone`, and the rate rebuild.
- The `fx.delay.feedback` row.

Each of those sends `effectiveFb() = clamp(washFb ?? p.feedback, 0, .9)`. Native sends the raw `p.feedback`, and the
comment at line 76 says "T14" but nothing implements it.

Failure: a song switch while a wheel routed to `macro.wash` is up, with the same wash fb before and after. Native
`applyAll` resets the feedback to the raw value, and `Perform::applyFxWheels` sees an unchanged `washFb_` and does not
resend. The echo tail loses the wash until the wheel moves. The same happens on any feedback, tone or pingpong edit
during a wash.

Change (two lines). `Perform::delayFeedback()` now exists:

```diff
@@ void applyAll(Model &m, double when) {
-  sendOp(m, DelayOp::ApplyAll, when, delayEffectiveTime(p, m.song().tempo), p.feedback, p.tone, p.pingpong ? 1 : 0);
+  sendOp(m, DelayOp::ApplyAll, when, delayEffectiveTime(p, m.song().tempo), m.perform().delayFeedback(), p.tone,
+         p.pingpong ? 1 : 0);
@@ onSet
-    sendOp(m, DelayOp::SetFeedback, req.when, p.feedback, 0.0);  // T14: lerp(fb, .75, wash) while a wheel washes
+    sendOp(m, DelayOp::SetFeedback, req.when, m.perform().delayFeedback(), 0.0);  // audio.js setParam: effectiveFb
```

Plus `#include "model/perform.h"`.

Preconditions:

- At delay `onCommit`, `SongGraph::routing()` must already be the committed routing. That matches audio.js, where the
  routing state is set before `_applyFx`.
- `m.perform()` must exist when `applyAll` runs. `perf_` is built at the end of the Model constructor, so check that
  no `applyAll` runs during service construction.

No fixture sets both a wash route and a delay change, so renders should not move. Re-check `golden.t05` and
`golden.t13`.

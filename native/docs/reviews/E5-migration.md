# Lane E5 (1.x → 2.0 library migration): skeptic review, 2026-11-25

Verdict: **VERIFIED, with two fixes and two open items.**

The builder's five data-loss fixes hold. Each one survived a direct attempt to break it. The fixtures really are 1.x
output: a from-scratch regeneration of `rich` and `pristine` (v1.1.0) matches the committed files once ids and
timestamps are normalised. The `replacePristine` decision is safe as a tier-2 change.

This review found and fixed two real ways to lose data in `controller.importLatestBackup`, each with tests that fail
without the fix:
- **M1**: an edit made while the pre-import backup was being written was lost.
- **M2**: two imports at once.

Two open items are outside this lane's code and need an owner's call:
- **M3**: a library grown past the 2 M cap by edits cannot restore its own backup.
- **M4**: going back and forth between 1.x and 2.0 Chrome on the same origin twice deletes both libraries'
  hidden copies.

Tree: `/home/claude/wt-e5`, branch `lane-e5`, uncommitted on `10c3ec7`, plus this review's edits. Playwright used
`PLAYWRIGHT_BROWSERS_PATH=/root/.cache/rig-pw`, and nothing was installed. Suites ran one at a time on a shared 2-CPU
box.

- Generated by `git archive <tag> app server.js package.json docs` of v1.1.0 `c8704a7` and v1.0.0 `b3d0758`, each

- Only the `downgrade` case uses this checkout's store, and it is labelled as such.
- The files are schema 1, which a 2.0 store can never write.
- Every file is under 200 KB. Only `huge` is gzipped (21–24 KB).

## Findings

**M1 (Medium, fixed): an edit made while the pre-import backup is written was in neither the backup nor the
library.**
- `backupNow()` serialises the library and then awaits the shell, which is an IPC or `WKScriptMessage` reply.
  `importLatestBackup` then replaced the live library.
- A store write in that wait was lost for good: a learned MIDI fader (`controller` line ~1291), a scene save or
  adjust, or a menu-bar command.
- Probe: write during the pending backup → `{inBackup:false, inLib:false}`.
- Fix: back up again while the library content changed underneath, at most 3 times; otherwise refuse with
  `backup failed` and the message "Your library kept changing…". "Content" means songs, the orders, setlists and the
  settings that are not device-local, compared by reference (the state is frozen). A device-local write such as
  `midiInputName` does not count.

**M2 (Low–Medium, fixed): concurrent `importLatestBackup`.**
- A menu fired twice, or the Settings button pressed while the menu import runs, started two imports.
- Each wrote a pre-import backup, and the native rotation keeps 3.
- In the native shell the staged file is served once, so the second import got `latestAnywhere()`. That is the newest
  own or Electron backup, and it replaced the picked library after the first import finished. With the stand-in it
  imported the Electron `deleted-factory` library over the picked `rich` export.
- Fix: one import at a time. A second call returns the running call's promise, and the guard is released after a
  throw (tested).

**M3 (Medium, open, pre-existing security S2): a library grown past `LIBRARY_MAX_CHARS` cannot restore its own
backup.**
- Ordinary writes are not capped: notes are 10 000 characters per song, and `addSong` and duplicate add more. Only
  charts check the cap (`chartOverflows`).
- `importJSON` refuses anything whose library exceeds 2 000 000 characters.
- So a ~1.94 M-character library like `huge`, with 12 notes filled in 2.0, is 2.02 M. Its own backup and export are
  then refused as "too large". This includes the pre-import backup that E5's safety story relies on.
- Real Chromium holds 3.88 M characters of this origin without trouble (measured below), so the cap is a margin, not
  the quota.
- Not fixed here, because it is a policy call for the S2 owner / Ryan. Options:
  - (a) Refuse or warn on writes past the cap, at persist time, where the JSON is already built.
  - (b) Let a replace import go to about 1.1× the cap.
- `skeptic.test.mjs` has it as a `todo` test.

**M4 (Medium, open, pre-existing UIA × 1.1): Chrome same-origin ping-pong between 1.1 and 2.0.**
- Run with the real 1.1 store (`git archive v1.1.0 app/js`) on one storage, after a 2.0 edit:
  1. 1.1 starts. It sees a future schema, keeps the 2.0 text under a backup key and seeds factory songs into `rig.v1`.
  2. 2.0 then shows **19 factory songs (pristine)**, and the 2.0 library is only in that hidden key.
  3. After the second round trip **both the 1.x copy and the 2.0 copy have been pruned** (`BACKUPS_KEEP = 3`,
     because each side adds a key per launch).
- No UI restores a `rig.v1.backup-*` key.
- Native and Electron 2.0 are not affected: they use a different origin from 1.x Chrome.
- The release notes now warn about this and say to export first.
- A code fix needs Ryan's call. For example, 2.0 could offer to restore when it loads a pristine schema-1 seed while a
  newer schema-2 backup key exists.

**M5 (Low, pre-existing): unknown top-level fields are kept in the state but not exported.**
`exportJSON` writes only the known top-level keys, so a `futureTop` key survives a replace import and a reload, but
not a backup or an export. 1.x never wrote one, and its envelope keys are stripped on purpose (fix 4). Unknown fields
at every other level survive replace, merge (song and setlist level), reload and export → re-import (tested:
15 levels).

**M6 (Info): a replace at the cap can end a few characters past it.** The cap counts the incoming library, and the
kept device-local settings of this machine come on top (+136 characters measured). This is right as it is: it is
what keeps a backup of a library under the cap restorable. Tested so it stays that way.

**M7 (Low, docs, fixed):**
- The release notes said 1.x writes a backup "about 30 s after an edit". 1.1 writes one on window close, ≥ 60 s after
  a session's first edit, then at most every 10 min, and 30 s after launch. SHELL.md said "every edit + 30 s".
  Both are corrected.
- The release notes did not mention M4 or the theme (M8). Both are added.
- The "does not move" list matches 1.1's `DEVICE_LOCAL_SETTINGS`, checked against the 1.1 source.

**M8 (Low, design note on O-AW-E5): a theme picked in 2.0 is overwritten by a pristine replace.**
`theme` is a LOOK setting, so it does not clear `pristine`. The replace then takes the file's theme, or the default
when the file has none. This is not library content, and it is now in the release notes and DECISIONS.

**M9 (Info, UIA by design): a schema-1 or schema-less file with more than 4 slots is cut to 4.**
1.x never writes one. Only hand-written files and JSON arrays of songs, which are read as legacy, are affected, and no
2.0 code produces either. Song files and library exports carry `schema`.

**M10 (Low UX, not fixed):**
- When the pre-import backup fails, Settings › "Import latest backup" toasts "The backup could not be imported…" next
  to the controller's accurate warning.
- main.js's "Use that library" banner has no try/catch. It only matters if the store throws, which the probe had to
  force.

### Attacks that did not lose data (each pinned by a test in `skeptic.test.mjs`)

- **Setlists naming deleted songs** are filtered. A song listed twice in a set stays twice, on both replace and
  merge. **Duplicate ids** in `songOrder` are deduplicated, and array libraries get `x~2`. A `currentSongId` that
  names a deleted song falls back to a song that exists.
- **midiLearn odd keys** (dots, emoji, spaces, `0`, `slots.7.gain`) are kept. `__proto__`, `constructor` and
  `toString` are refused (L2), and nothing pollutes the prototype.
- **Missing user-sample packs and unknown instrument ids** keep their reference, including unknown sub-fields. Nothing
  is swapped for a default.
- **NFC and NFD names** come through byte for byte. Merge treats them as different setlist names, so no
  "(imported)" suffix is added.
- **Factory songs** that were edited, reset, renamed or deleted in 1.x keep that state through the import and two
  further `seedFactory` launches. Nothing is re-added, because the factory version is 2 on both sides.
- **A crash in the store write after the backup**: the library is unchanged and the backup restores it.
- **localStorage quota on the replace** (setItem throws): `setItem` is all or nothing, so the old library stays
  whole on disk, the user is warned, and a "crash" reload gets the old library. The save goes through once space
  allows.
- Real Chromium: `huge` on the same origin, plus its migration copy, is 3.88 M characters, and the edit and replace
  saves succeed. With one more ~1.9 M backup key the migration copy is skipped with a console *warning* and the
  upgrade goes ahead. The downgrade copy is lost in that case; the library itself is not.
- **The 30 s debounce backup racing an import**: the pre-import backup comes first and the timer backs up the
  imported library afterwards. Ordering is safe. The native rotation pressure this adds is in the open items.
- **`dryRun`**: no `setItem` or `removeItem`, no subscriber event, no generation bump and no `meta.edited` change.
  This holds for 9 inputs × 3 options, on both pristine and edited stores. `importLatestBackup`'s dry check writes no
  rotation file (the builder's test). Its failure warning is the intended UI message.

### O-AW-E5 (`replacePristine`): tier 2 confirmed

- **Detection is robust.** Every library-content write clears `pristine`, and the merge was asserted to leave every
  pre-existing song and setting intact. Writes tested: a setting (latency), the library order, a setlist order, a new
  setlist, MIDI Learn, Program Change, pedal, view, a chart, a deleted song and a song level.
- **It persists both ways across a relaunch.** The logic is the same as 1.1's `isEditPath`.
- **What still counts as pristine:** navigation, device-local settings (asserted kept by the replace) and the theme
  (M8).
- **No backup is written on this path, and none is needed.** A pristine library holds nothing of the user's except
  the theme. The factory songs can be re-added from Edit › Factory….
- **The toast** ("Library imported: N songs, M setlists") is adequate for an explicit file pick. A confirm dialog
  would protect only factory content.
- **Conclusion:** the rule "irreversible changes to user data are tier 1" is not triggered, so tier 2 stands.

### Downgrade (checked against the 1.1 code)

The claims hold, run with the real 1.1 store and the recorded in-app run:
- 1.1 refuses a 2.0 file with "newer version", does not throw and leaves the library unchanged.
- A schema-2 `rig.v1` is kept aside and a factory seed is made.
- `schema` edited to 1 cuts slots 5 and up and keeps the 2.0-only fields as unknown fields.

What was missing is M4. One more fact for the record: 1.1's own `importLatestBackup` still backs up before it checks.
It cannot be changed, and 1.1 never sees 2.0's native backup folder.

  - M2: a single-flight guard. The function is split into `importLatestBackup` and `importLatestBackupOnce`.
  - `DEVICE_LOCAL_SETTINGS` is now imported from `store.js`.
- `test/phase2/migration-1x/skeptic.test.mjs`: 17 tests (16 pass, 1 todo). Both M1 tests and the M2 test fail with
  the controller put back.
- `native/docs/RELEASE_NOTES_2.0-migration.md`: backup timing, the theme, M1 in Safety, M4 in "Going back".

## Open items

1. **M3** (S2 owner / Ryan): over-cap libraries and backups that cannot be restored.
2. **M4** (Ryan): Chrome same-origin 1.1 ↔ 2.0 ping-pong prunes both hidden copies. 2.0 has no restore UI for
   `rig.v1.backup-*` keys.
3. **Addressed by lane F1, pending CI** (Swift is not compiled on Linux; the macOS `mac-check` job builds it and the
   E4 self-test exercises it). `RigBackups.payload` now requires `isLibrary`: a JSON object (`JSONSerialization`, as
   `stage(fileURL:)`), a whole library (`songs` object / array or `kind` "library", not a song file) and `schema`
   absent or ≤ `maxSchema` (2, store.js `SCHEMA`). `latestAnywhere()` serves the newest such file (mtime, then name)
   and the first-launch offer dates the same file. The self-test fixture gained a newer truncated
   `rig-20261201-120000.json`, so the `migration` step fails if it is served. JS stand-in and tests updated
   (`lib.mjs`, `paths.test.mjs`, `selftest-scripts.test.mjs`). The original finding:
   - It returns the newest *readable* file even when it is truncated JSON. JS now refuses it safely, but the older
     good Electron backups are never offered.
   - It should skip files that `JSONSerialization` cannot parse, as `stage(fileURL:)` already does, and then serve
     the next one.
4. **Addressed by lane F1, pending CI: the native rotation keeps 10** (`RigBackups.keepLibrary`, as main.js;
   DECISIONS O-AW-F1, tier 2: chosen over a separate pre-import file). The original finding: **native rotation keeps
   3** (E4/Apple, the builder's finding, confirmed). After a replace, the debounce timer's
   backup of the imported library plus two more push the pre-import backup out. With M2 fixed, one import now writes
   one backup. Consider keeping 10, as main.js does, or keeping a `rig-preimport-*` file apart from the rotation.

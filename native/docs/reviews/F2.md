## Findings

**K1 (medium; fixed): a rescan that clears failure marks was not reported.** A failure mark reads as settled, so a
sampler whose every sample failed reads `loaded: true`. `invalidate` (My Samples rescan) erases the marks, which
turns it `false`, but only urls whose *entry* left the cache reached `dropped_`, and such a sampler has none. The
stress found it on the builder's code at once (`user:g shim true truth false`, seeds 2 and 1001). The shim's own
`reloadManifests` re-asks for every id it knows, so the Settings rescan path self-heals there. A `rig_set_paths`
rescan the shim did not start, and any future caller, did not.

**K2 (low; fixed): a rescan that changes a manifest was not reported.** A sampler that gains a url (never decoded)
turned `false` with nothing dropped. A sampler the rescan removed reads `true` (unknown), but `usesAny` returned false
for an unknown id, so a `false` last word stayed. Both mutants fail the extended stress (`user:h`, seed 1).

**Fixes.** `invalidate` puts every invalidated url in `dropped_`, and `usesAny` re-reads an id the registry no longer
knows (the diff still decides; an unknown id reads `true`). Cost: one set insert per user url per rescan, one cheap
re-read per unknown known id on a tick with drops.

**Convergence (verified).** A new seeded stress (`samples_service`, offline 60 seeds × 150 steps, realtime 25 × 120 in
CI; 1500 + 1500 seeds run here, 0 failures) walks preloads in every pin mode, one-sampler `sampleStatus`, soft-cap
changes (evictions at the cap), memory pressure 1 and 2, rate changes with a rebuilt unit's decodes in flight across
ticks, low resource, the playing song + protect, hard-cap refusals (419 + 281 in the long run), a partial and a total
decode failure, rescans (failure marks cleared, manifest changed), and units holding buffers across a rate change
(`stale_`). After every step's control turns, every known sampler in a shim model equals the truth, computed from the
cache's own lookups rather than `statusOf`. Each tick sends at most one event, and that event names only known ids
whose value moved. Never-reported ids are never named.

**Paths checked by reading.**
- **Transient failure, 30 s window: not a gap.** The builder lists it as unreported. `failed()` does not look at time.
  The mark stays until `requestJob`'s `skipped()` erases it, and that request belongs to a preload, a prepare, a
  re-warm or a rate-watched rebuild, which reports. The CONTRACT_CHANGES and SHELL.md wording is corrected.
- **Pinned sampler losing a buffer** (protect-pressured eviction, trim level 2): through `deleteEntry`, so it is
  covered.
- **`supersede`** has no caller outside tests, and its `deleteEntry` is covered anyway.
- **Ordinary decodes outside preload / prepare / re-warm / a rate watch are not reported.** This is by design, and
  none exists in the app.
- **`reported_` is never erased.** It is bounded by the distinct sampler ids ever named (library songs, user packs,
  plus any unknown id a client asks `sampleStatus` about). That is ~100 B each. No practical leak, but a buggy client
  could grow it. Open item 2.

**Threads (verified).** `dropped_`, `landed_`, `reported_` and the watch flags are touched only by `BufferCache` /
`CacheServiceImpl` methods that run on the control thread: pump, op handlers, host calls through `onControl`, and
garbage drain. Inline offline, the posting thread is the control thread. Workers only push into `mailbox_` under
`mailM_`. TSan: see the gate.

**Emission storm (none).** The idle tick costs two compares. Drops in one turn give one event. A big warm loop at
the cap added 15 events over F1 in ui-core. During a rate watch, every turn where a decode lands re-reads all known
samplers (0.78 ms for the factory set). A rate change during an 8-song pinned warm therefore costs about 1 ms of
control-thread time per landed decode until the warm finishes, with events only on real changes. This is acceptable
and noted (open item 3).

**BOM (Swift, by reading).** `isLibrary` checks `data.starts(with: [0xEF, 0xBB, 0xBF])` before `JSONSerialization`.
That is correct and cheap, and `payload` and `stageOfferedAndImport` both go through it.
- **Does `String(data:encoding:.utf8)` keep a leading BOM?** Best knowledge, about 65 % confidence and not verified
  here: on Apple platforms it **strips** it. NSString/CFString's UTF-8 decode skips a leading EF BB BF, and as I recall
  swift-foundation's rewrite kept that for compatibility.
- **If so, the F1 premise is off.** Before F2, a BOM'd backup was most likely served *without* the BOM and imported
  fine, not "served and then refused". Either way the new check makes the outcome deterministic, and it is stricter
  than before: skipped, and an older good file served. That beats Electron, which refuses it.
- **`stage(fileURL:)` now refuses a leading BOM too** (same dialog, "not a Worship Rig library backup"). Without
  this, whether a picked file imports would depend on Foundation's BOM handling. The JS stand-in (`lib.mjs` `pick`:
  utf8 read + `JSON.parse`) already refused it. A new migration-1x test pins that.

## Open items

1. **Ordinary decodes stay unreported by design.** If a future feature decodes outside preload / prepare / re-warm
   (for example lazy zone loading), it must emit or set the rate-watch style re-read.
2. **`reported_` never shrinks.** Bound it, for example by dropping unknown ids on a rescan, if clients ever send
   arbitrary ids.
3. **Rate-watch cost scales with known samplers × landed decodes.** About 1 ms per landing for the factory set.
   Narrowing the re-read to samplers that use the landed url would make it O(1). Not needed today.
4. **Swift BOM behaviour** (`String(data:)`) is unverified. The byte checks make it irrelevant to the outcome.
5. Inherited from F1: no iOS compile proof (`apple-sim` is environment-only).

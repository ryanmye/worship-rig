## Findings and fixes

**DS4 (privacy, 1.1.1, fixed).** I judged the builder's item 10 too broad. Export library is the one file a user is
told to share (Chrome ↔ Mac app), and it named the hardware and `/Users/<name>/…`. Bluetooth MIDI devices are often
named after their owner too.
- There were two options. The `~` substitution hides the account name only: device names stay, and 2.0 would need to
  expand `~`. Making the block opt-in in Export removes all of it from the shared file, and nothing is lost:
  - backups carry the block;
  - 2.0 Chrome on the same origin reads `rig.v1` directly;
  - the one case that needs a file, Chrome 1.1.1 → the 2.0 Mac app, turns the toggle on.
- I chose opt-in. The change is a `C.toggle` (`data-testid="export-device"`) after Import… and a one-line hint. The
  Edit view's setlist export never writes the block.
- Release notes, CONTRACT_CHANGES and README are updated.
- The browser test checks that the default download has no block and no device name anywhere, and that the download
  with the toggle on has the block and its `rig.install` marker.

**Install id.** 128 random bits (`crypto.getRandomValues`), kept in localStorage per origin, read only by store.js and
never sent anywhere (grep: no fetch, update check or server use). It cannot link a person across sites. It does link
files from one install to each other, which is its purpose. With DS4 it no longer appears in a default export.

**DS1 (no overwrite, 2.0, fixed).** `deviceSettingUnset` read "back at the default" as unset. So turning menu-bar
mode on and off, clearing the click, choosing a MIDI input and going back to "first", or deleting a keyboard curve
were all undone by a later 1.1.1 backup.
- Fix: `store.set` and `store.update` record each device-local key this machine changes in localStorage
  `rig.device.touched`. This is outside the library, so it is never an edit and is never exported. Keyboards are
  recorded per name, and `midiInputName` is excluded because the controller writes it.
- `deviceSettingUnset(…, touched)`, `store.applyDeviceSettings` and `controller.applyDeviceSettings` all honour the
  record. A keyboard deleted here stays deleted. A read-only window keeps the record in memory only.
- Residual: changes made in a pre-D11 2.0 build were never recorded.

**DS2 (other machine auto-applies, 2.0 + Swift, fixed).** `latestAnywhere()` tagged every result `via: 'backups'`. On
the iPad that folder is `Documents/Backups`, which is open in Files (`UIFileSharingEnabled`). A Mac's 1.1.1 backup
dropped there applied by itself.
- Swift now tags it `'files'` on iOS.
- `backupFromThisMachine` also refuses everything when `rig.platform === 'ipados'`. 1.1.1 never runs on an iPad, so
  this holds even with an older shell.
- I traced every other path:
  - menu bus `importLatestBackup`: staged or `latestAnywhere`;
  - AirDrop, Open in and the macOS / iPad pickers: `'picked'`;
  - first launch: `'first-launch'`, the Electron folder on this Mac;
  - main.js "Use that library": Electron, its own folder;
  - `restorePreviousLibrary`: goes through `importJSON`, whose `deviceSettings` result is ignored;
  - Settings › Import…: offer only.
- No other path auto-applies a foreign file.

**DS3 (stored block, 2.0, fixed).** 1.1.0, and 2.0 before D11, keep an imported 1.1.1 file's block as an unknown
top-level field, so `rig.v1` and kept copies can hold another machine's device data. The 2.0 load, `reload()` and
`update()` paths kept that field in state, against claim 4. `migrate()` now drops `deviceSettings`, and `importJSON`
reads the block from the file. Tests:
- the real `git archive v1.1.0` store imports a 1.1.1 file, and 2.0 loads that storage without the block;
- `migrate.test.mjs`'s lossless filter allows this one deliberate drop.

**DS5 (UI, 2.0, fixed).** In the offer row the checkbox was 13 px, the buttons 36 px, and `.st-restore{display:flex}`
beat `[hidden]`. Now:
- the whole label row is 44 px tall and the box is 22 px;
- Import and Cancel are 44 px;
- `.st-import-offer[hidden]` hides the row.

Measured in Sanctuary (the default), Daylight Day and Sanctuary Day:
- the targets are 44 px tall;
- every control has a label ("Also use its device settings here (only ones not set on this computer yet)");
- text contrast is 14.0 / 14.3 / 13.7 : 1;
- zero console errors.

I looked at the screenshots: the layout is clean in both the dark and the light themes.

**Confirmed as claimed:**
- Claims 1–3, 5–7 and 9. Device-local writes never mark the library edited: `isEditPath` excludes them, and a test
  covers it.
- A second or read-only window applies nothing (controller and store).
- A replace import keeps this machine's values: `keep`, then a fill of unset keys only.
- Compatibility:
  - 1.1.0 and pre-D11 2.0 tolerate the block;
  - 1.1.1 refuses a 2.0 file;
  - the D8 guard holds through 2.0 → 1.1.1 → 2.0 → 1.1.1 → 2.0;
  - the D8 random test passes with 1.1.1 exporting blocks.

**Swift `via` (claim 8).** It is correct and minimal: three assignments (now four with the iOS branch) and a comment.
It never changes which file is served. JS treats any unknown `via` as another machine, so it fails closed.

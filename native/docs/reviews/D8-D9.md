## Findings

**K1 (High under full storage, fixed): Restore previous library… could delete the copy it was restoring.**
- `restorePreviousLibrary` keeps the current library first (`keepCurrent`). When that write hit the quota, the
  policy removed the oldest superseded copy.
- When the user restores an older copy (e.g. the real 2.0 library that 1.1.0 set aside), that copy is exactly the
  oldest superseded one. It was removed, then `restoreKept` failed with "That library is no longer kept."
- The user's chosen library was gone, and a toast said storage was full.
- Fix: `keepCurrent(kind, {protect})`. The controller passes the target.
- Test: `d8-skeptic.test.mjs` K1 (failed before the fix).

**K2 (Medium, fixed; policy change for Ryan to note): "superseded" was by schema only.**
- Copies of one schema are often different libraries. 1.1.0 seeds the factory songs each time it sets a 2.0 library
  aside, so a later set-aside copy is usually a factory seed plus a few edits.
- With the old rule, a failed save removed the oldest non-newest copy of its schema: a 300-song set-aside 2.0
  library while the factory-seed copy stayed. The same rule also contradicted D8's "a migration copy is never
  pruned".
- Fix: a copy is removable only when every song id and setlist id in it is also in either:
  - a newer kept copy of the same schema, or
  - for a 2.0 copy, the main library, both as stored and as about to be saved. Using both means a failed write
    cannot drop it.
- The newest copy of each schema still always stays.
- When nothing qualifies, the write fails as before. A failed save keeps its retry and warning, and the main key
  keeps the last good save. A failed `keepCurrent` replaces nothing.
- Trade-off: a full profile now refuses the save rather than delete a different library.
- Tests:
  - d8-skeptic K2.
  - Real Chromium at real size (`quota.pw.mjs`; quota measured at 5 241 856 characters): the earlier state of the
    same library goes, the different one stays, the next copy is refused with nothing removed, and the save that
    cannot fit leaves `rig.v1` byte-identical and loadable.
  - kept.test's two quota tests now use a grown copy of the same library as the newer copy.

**K3 (Low, fixed): a second 2.0 window taking over (`reload()`) did not keep the 1.x text.**
- If a 1.1.0 window saved after the 2.0 window loaded, 2.0's upgrade was saved over that 1.x text, and no 1.x copy of
  it was kept. (Its content stayed reachable in 2.0's main library.)
- Fix: `reload()` keeps a `migration` copy, as load does. It does not keep one for a seed or an already-kept text.
- Test: K3 (kept once, not twice).

**K4 (Low, open, 1.1.0 only; 1.1.1 fixes it): a waiting 1.1.0 window that takes over after 2.0 closes.**
- 1.1 and 2.0 share the `rig-instance` lock, so a 1.1.0 tab opened while 2.0 is running waits read-only.
- 1.1.0 set aside the 2.0 library as it was at 1.1.0's load. On takeover, its `reload()` refuses the newer schema,
  and its next save writes its seed over `rig.v1`.
- 2.0 edits made in between are then lost. The test shows the loss with the real 1.1.0 store, and none with 1.1.1.
- Needs both versions' pages open on :8437 at once, which needs one server stopped and the other started under an
  open page. 2.0 cannot prevent it. Covered by "Keep your last 1.x export" in the release notes. 1.1.1 is the fix.

**K5 (Info): copy and UX, not changed.**
- 1.1.1's banner returns on every launch while `rig.v1` holds a 2.0 library. That is accurate, but repeated.
- 2.0 lists 1.1.1's `.1x` library even when it is an untouched factory seed. It shows as "in use", not a date.
- Once a 2.0 library is past 2 M, every merge import is refused, even one song: "That file is too large… about 2 MB".
  The rule is D9's, but the message blames the file.
- `tooBig` says "about 2 MB" for replace imports too, which are allowed to 2.5 M.

**Checked and held (no defect):**
- Adoption at load: 40 rotation keys (1.x and 2.0 libraries, identical texts, truncated text, non-library JSON) plus
  a pre-existing kept copy, over 4 loads.
  - Idempotent: the same kept set after every pass.
  - No duplicates, nothing dropped, and every timestamp kept.
  - Unreadable keys stay in the rotation.
- Random quota fills, 60 seeds:
  - The newest copy of every schema that ever had one stays.
  - A failed save leaves `rig.v1` byte-identical.
  - The next load always opens the last good save.
  - No kept copy is ever truncated.
- `restorePreviousLibrary`:
  - A crash after the kept copy, or after the replace but before the save, reopens the pre-restore library, with
    both copies kept.
  - A read-only window and a second window (lock held) refuse with `read-only` and write nothing.
  - Undo brings the pre-restore library back exactly, apart from `meta`.
  - A 2.47 M copy restores over an edited library and survives a reload, in real Chromium. In a 5.2 M stand-in too.
  - In a 3 M stand-in, either it is refused, or the save fails with `rig.v1` intact, or (when it fits) the target
    is now `rig.v1`. The target is never lost.
- D9:
  - 40 over-cap saves with the controller: every edit is saved.
  - Toasts at 2.0, 2.2 and 2.4 M only (each at least 10 % above the last), with no repeats in between.
  - A merge and a song file above 2 M are refused, also as `{replace:true}`, because a song file is not a whole
    library.
  - The 2.4 M library restores.
- The 1.1.1 banner text matches what the store does: "kept untouched", "a separate 1.x library (the factory songs)"
  the first time. The 1.1.1 release notes and the 2.0 release notes describe it correctly.
- 1.1.1's store never writes, backs up or prunes `rig.v1` or `rig.v1.backup-*` while `rig.v1` holds schema 2.
  - Its own backups are `rig.v1.1x.backup-*`, outside both versions' rotation prefix.
  - 1.1.0 after 1.1.1 is covered by the random sequences (more than 50 such steps).

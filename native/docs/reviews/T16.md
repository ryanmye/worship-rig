### fx-row-sweep, checked against the builder's claim

Per 0.5 s window, golden vs native, from the first window on:

- RMS: −21.89 vs −20.03, −20.89 vs −19.24, −24.09 vs −23.28 dB, and so on.
- The gap closes by about 3.5 s.
- From 7.5 s on, the max abs diff is ≤ 1.3e-5. That stretch includes the drone row events at 10.5–11.1 s, and the
  drone dominates once the sampler has decayed.
- Golden frames 4000–4400 are exactly 0; native is non-zero on 399 of them.

To test the drone's part, I rendered a no-drone variant (drone `mode: off`, drone events removed):

- Its first-window RMS is −20.03 dB, the same as with the drone.
- Its max difference from the with-drone render in 0–0.5 s is 1.2e-3.

So the early excess does not come from the drone. It belongs to the sampler / lofi / fx-rows-before-start path
(T05 / T13 / T12). PARITY.md already listed the same 1.22e-1 before T16.

## Fixes made in this review (T16-owned files)

1. **F1, MEDIUM (bug, fixed).** `DroneCore::buildInst`, the out-of-slots path, cuts the oldest fading layer and gives
   its slot to the new layer. The cut layer's `fadeOutLayer` timers still held it with the old slot number. When
   they fired, they sent `AllOff` to the reused slot and then `returnInst` on it, which disarmed it or dropped its
   instrument. Result: the live drone went silent (0 live voices).
   - Reproduced with 30 key changes 0.1 s apart under a 6 s fade: −66.8 dB in 7.0–9.4 s, `liveVoices() == 0`.
   - Fix: the cut layer gets `pe.slot = -1`, and both timer stages return early on a negative slot.
   - Regression test in `unit.drone`: "slot pool full: a cut fading layer's timers leave its reused slot alone". It
     also checks that the cut path ran. It fails without the fix and passes with it.
2. **F2, LOW (contract, fixed).** `renderDroneLoop` calls `DroneUnit::process` / `ReverbUnit::process` directly,
   outside `rt::RenderScope`. T04 review finding 2 says every direct render entry needs FTZ/DAZ: without it the
   HPF/LPF/convolver can run on denormals.
   - Each quantum's two `process` calls now run inside a `RenderScope`. `NullEvents::garbage` reserves 256 entries,
     so nothing is allocated inside the scope.
   - `unit.drone_freeze` now asserts `g_rtAllocs` is unchanged across three loop renders.
   - The freeze goldens are unchanged (same max diffs).
3. **F3, test.** `unit.drone_cpu` timed `DroneUnit::process` without FTZ or the allocation trap. It is now inside
   `RenderScope` and asserts zero audio-thread allocations. The header no longer claims a pad case it never ran.
   - Measured on this box: 1 layer 33 µs, crossfade 66 µs, 9th 40 µs, frozen loop 2.2 µs per 2902 µs quantum.

## Checked, no finding

- **Real-time safety.**
  - `DroneUnit::process` / `apply` use only fixed arrays and stack buses, and `wa::Param` has fixed capacity.
    Payloads travel as `Owned` and go back through `giveBack`. No locks, no unbounded loops.
  - The worker thread and mutex are control-side only. `renderDroneLoop` and pad decodes run on the worker in
    realtime and inline offline.
- **Async lifetimes.** Every timer and worker continuation checks `alive_` and a sequence number.
- **Ports.**
  - `makeSeamlessLoop` / `seamCorrelation` / `seamCheck` / `freezeLoopFrames` follow drone-freeze.js, with ρ per
    channel and `js::sin/cos`.
  - `setParam`, `levelTarget`, `gainChanged` / park and `setFrozen` follow drone.js.
  - HPF 80 Hz uses Q `20·log10(√½)` dB. Width ramps use τ 20 ms (contract 3.9).
- **Coverage.** All nine JS tests named in BUILD_PLAN are ported. The `config {droneFreeze}` bridge row, schema and
  contract row are present.

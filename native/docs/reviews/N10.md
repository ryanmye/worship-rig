## Event × ref matrix (what runs, from the files at the ref's commit)

GitHub reads a workflow from the commit of the ref that triggered it: the tagged commit for a tag push or a
`release` event, and the "Use workflow from" ref for a dispatch. So every row holds only for commits that carry
lane-n10's files. See O2.

| event / ref | release.yml (Electron) | release-native.yml |
|---|---|---|
| push tag `v1.x` | build + release (as main) | not triggered (`v2.*` only) |
| push tag `v2.x`, `v2.x-pre`, `v3.x`, `v10.x` | not triggered (`tags: ['v1.*']`) | `v2.*`: mac + ipad, **no release** (job `if` requires dispatch); v3/v10: none |
| `release: published` `v1.x` | build + release (as main 261ea8d) | no `release` trigger |
| `release: published` `v2.x`+ | triggered, both jobs skipped (`refs/tags/v1.` guard on each job) | no trigger: nothing attached |
| push branch `v2-native` touching the 3 release paths | not triggered (tags only) | mac + ipad, no release |
| push other branches / other paths | not triggered | not triggered |
| dispatch on a branch (any `dry_run`) | build only (dry run, as main) | mac + ipad; `publish` gives a warning and no release |
| dispatch on tag `v1.x`, `dry_run` false / true | build + release / build | that commit has no release-native.yml |
| dispatch on tag `v2.x`, `dry_run` any | both jobs skipped | publish off: mac + ipad; **publish on: mac + ipad + release** (the only publish path) |
| release created by the release job (GITHUB_TOKEN) | no run: GITHUB_TOKEN events start no workflows, and the gate would skip it anyway | n/a |

`release`'s `if:` has no status function, so GitHub's implicit `success()` applies: it needs a green `mac`. In `mac`,
the self-test step fails the job (no continue-on-error), and so does a skipped self-test (the result step requires
`selftest.json`). `ipad` is `continue-on-error` and `release` doesn't need it. `latest` reaches `gh` only as
`--prerelease=false --latest` under `[ "$LATEST" = true ]`. Otherwise the release is `--prerelease`, which GitHub's
`/releases/latest` skips. Secrets: `GITHUB_TOKEN` only (now tested). Permissions: top-level `contents: read`, and
`contents: write` only on the `release` job of each workflow (tested). There is no `pull_request*`, `workflow_run` or
`repository_dispatch` trigger (tested).

release.yml vs main 261ea8d: apart from comments, the diff is exactly the `v1.*` tag filter, the new job-level `if`
on `build`, `refs/tags/v1.` on the version step and on the `release` job's `if`. Steps, matrix, names, notes and the
reuse-existing-release block are byte-identical, so it is a faithful copy and v1.x behaves as on main.

project.yml: `MARKETING_VERSION: "2.0.0"` and `CURRENT_PROJECT_VERSION: "1"` sit in the project-level
`settings.base`, which covers Debug and Release for both targets. XcodeGen writes the two `$(…)` strings into the
generated Info.plist verbatim (it is a plain YAML string, no quoting needed). Xcode expands build settings in
`INFOPLIST_FILE` at build time for every configuration, so mac-check's Debug build is unaffected. package-release.sh
refuses a bundle whose version is still `$(`. The workflow's `sed` reads the same number, and the test checks that.

## Findings (fixed)

- **F1 (medium, fail-open) `release-notes.mjs --require-final` could pass a draft.** The "run as a script" guard
  compared `import.meta.url` (a realpath) with `process.argv[1]` (the path as typed). Reached through a symlink, the
  script skipped `main()`: empty stdout, exit 0. The release job would then have published an empty body, banner
  check bypassed. I reproduced it with a symlinked checkout. The CI runners' paths have no symlink, but a gate must
  not depend on that. Fix: compare realpaths. The release job also refuses a `notes.md` without its
  "Files (sha256)" section. Test: the CLI refuses the 2.0 draft and prints the preview, both directly and through a
  symlink. Mutation-checked: the old guard fails it. (762539b)
- **F2 (low) Link rewriting could produce wrong URLs silently.** It used WHATWG resolution against
  `github.com/<repo>/blob/<tag>/docs/…`. That turned a root-relative `/native/x.md` into `https://github.com/native/x.md`,
  and `../../X.md` into `github.com/<repo>/blob/X.md` (the tag dropped). Fix: `absoluteLink()` (exported)
  normalises the path within the repo. `/x` is repo-root-relative, as GitHub renders it. A path that leaves the repo
  throws. `?q` keeps the notes file, and `..` becomes `tree/<tag>`. The 2.0 draft's 3 relative links come out the
  same as before. (762539b)
- **F3 (medium) The "no My Samples / sound packs / user content" check was names only** (`user-samples`,
  `sound-packs`, `*.exs`). The bundle copies `app/` and `docs/` verbatim as folder references. The importer writes
  GarageBand conversions as `.m4a` / `.mp3`, and sound packs come as `.wav` / `.flac` / `.sfz`. None of these was
  caught if copied into `app/`, which matters most for a local run from Ryan's checkout. Fix, in two parts:
  1. A ban over the whole bundle on Apple and pack audio and instrument types (`.exs .caf .aif .aiff .aifc .m4a .wav
     .flac .ogg .sfz .aupreset .cst .pst .patch .band .logicx`) and on `pack.json`. The bundled samples are mp3 only;
     the test asserts that from the manifest.
  2. Every file under `Resources/app` and `Resources/docs` must be tracked in git (`git ls-files` vs `find`,
     `comm -13`). This catches a conversion even when it is an `.mp3`.

  I stub-ran it on Linux (fake codesign / hdiutil / ditto / lipo / PlistBuddy, the real tree from `git archive`):
  the clean tree packages; an untracked `.mp3`, an `.m4a` and a `sound-packs/` dir each fail with a message; a
  `.DS_Store` is ignored; a missing `Resources/docs` fails. (35dbf6e)
- **F4 (low) The 480 MB gate floored to whole MB.** A 480.0–480.99 MB app passed, while build-lint
  (`totalKB <= 480 * 1024`) fails it. It now compares KB. Stubbed `du`: 491520 KB passes, 491521 KB fails. (35dbf6e)
- **F5 (low) A `find` error made the script exit silently.** `leak="$(find … 2>/dev/null | head)"` under
  `set -euo pipefail` exited with no message on a find error. Errors now go into `$leak` and fail with a message,
  and a failing `git ls-files` or `find` in the new list step dies loudly. (35dbf6e)

Also: MAC_CHECK B3's gate list and CONTRACT_CHANGES "## N10" are updated (f69d9cd), and there is a test for
GITHUB_TOKEN-only secrets, no foreign triggers, `--latest` only via the input and no `gh release` outside the
release job (4dfa065).

## Observations (not changed)

- **O1** release.yml still builds the Electron app, as a dry run with no publish path, when someone dispatches it on
  any branch, `main` included after the 2.0 merge. This is main's behaviour today, kept on purpose ("v1.x as on
  main"). If that is unwanted after 2.0, gate `build` on `refs/tags/v1.` or on a `v1` maintenance branch.
- **O2** The gates are per commit. A `v2.*` tag on a commit older than this lane (v2-native ≤ 7e92df4, or main as it
  is now) runs the old `tags: ['v*']` release.yml. Today the backstop is the version check: package.json is 1.1.x,
  so the build fails and nothing is published. MAC_CHECK step 8.2 already says to tag only a commit that carries
  lane-n10's files. Keep it that way, and don't set package.json to 2.0.0 on an old-file commit.
- **O3** `latest` ticked on a `-pre` tag (for example `v2.0.0-beta.1`) makes a beta the "latest" release, and every
  1.1 install would then offer it. It is allowed because the input says so. A one-line refusal would be cheap if
  Ryan never wants that.
- **O4** Actions are pinned to major tags (`@v4`), and brew's xcodegen / ninja are unpinned, both as in
  mac-check / 1.x. The release job holds `contents: write`, so SHA-pinning its three actions (checkout, setup-node,
  download-artifact) is the cheap hardening.
- **O5** The link rewriter only handles inline `[t](href)`. Reference-style `[t]: href`, titled `[t](href "x")`,
  `<a href>` and images stay relative. An image would also need `raw.githubusercontent` to render, not `blob`.
  Links inside code spans are rewritten too. The 2.0 notes use none of these.
- **O6** Each dry run (a v2.* tag, or a v2-native push touching the 3 paths) costs two macOS jobs, mac and ipad.
  The paths list is narrow: the workflow, package-release.sh and `tools/release/**`. A change to `project.yml` or
  `check.sh` doesn't re-run the Release build, though mac-check still builds Debug. Adding `native/apple/project.yml`
  would catch Release-only breakage earlier, at about 2 macOS jobs per project.yml change.
- **O7** `package-release.sh --app` re-signs the given app in place. This is documented.

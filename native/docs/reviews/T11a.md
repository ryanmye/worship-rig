# T11a DSP sources: skeptic review

Verdict: **PARTIAL**. The four ports match Chromium 157 on every vector the builder wrote, and those claims reproduce.
Two Chromium behaviours were missing, and no vector covered them. Both are fixed in the owned files, and 9 new
vectors now pin them:
- the frequency param is clipped to ±Nyquist before detune;
- `automationRate = 'k-rate'` on frequency and detune, which voice.js uses with bend, vibrato and drift inputs.

One limit remains open: FM accuracy is bounded by the FFT deviation (see O1).

Reviewed tree: branch v2-native, working tree at about 23:00 on 2026-11-19, plus this review's edits. Build dirs:
- `native/core/build-t11a-review`: g++ 13, Release.
- `build-t11a-review-clang`: clang 18, Release.
- `build-t11a-review-asan`: g++, RelWithDebInfo, ASan+UBSan.

The Chromium sources compared are the 157 files the builder fetched into the scratchpad (`oscillator_handler.cc`,
`oscillator_kernel_sse2.cc`, `periodic_wave_handler.cc`, `audio_buffer_source_handler.cc`,
`audio_scheduled_source_handler.cc`, `constant_source_handler.cc`, `fft_frame.cc`, `rustfft_ffi.rs`). The behaviour
questions were settled empirically by running Chromium 157.0.8103.78 (the preinstalled Playwright build) through
OfflineAudioContext probes.

## Code review

- **Kernels vs Chromium source:**
  - The SSE2 k-rate float-lane kernel matches line by line: lane init `v + k*incr` cast to float, masked `r0` used
    for the fraction, `virtual_read_index += k * incr` in float then double.
  - The a-rate double-lane kernel matches: masked `r0`, `cvtpd_ps(x) - r0`.
  - `DoInterpolation` matches: the 2-point fraction uses the masked index, the 3- and 5-point `t` use the unmasked
    one, and the final double mix is cast to float.
  - So do the table selection (scalar and SSE forms agree, including ratio 0.5 for 0 and NaN), table sizes, range
    count, culling, normalization and the basic-wave coefficients.
  - `pow(2, -cents/1200)` uses `rig::js::pow`, a glibc pow port, which is what Chromium's libc `pow` is on Linux.
    There is no `fdlibm::` call in these files except BufferSource's detune (`fdlibm::pow`), and that one is ported.
  - The scheduling port (`UpdateSchedulingInfo`, `TimeToSampleFrame`) and BufferSource (fast path, interpolated
    path, loop wrap, grain clamp, negative rates, played-frames accounting) match the source.
  - The Chromium quirk where phase increments are not offset by the quantum frame offset (contract Q11, "phase
    advances through unstarted frames") is reproduced.
- **Real-time safety:**
  - `process()` does no allocation, takes no locks and has no syscalls. It uses only stack arrays of 128 floats.
  - Every loop is bounded. The fast-path while loop makes progress on each pass or breaks, and the negative-rate
    skip loop is bounded by the frame count.
  - The allocation trap is on in the test. PeriodicWave builds allocate, but only on the control thread.
- **Denormals:** FTZ/DAZ come from `rt::RenderScope`, as in the engine. No recursive state exists that could produce
  denormals.
- **Overruns:** every table index is masked, buffer indices are clamped to `max_index`, and `n` is capped at 128.
  This review fixed one possible overrun: `BufferSource::channels()` returned `SampleBuffer::channels` unclamped,
  while `f32[]` and `i16[]` hold 2 pointers. It is now clamped to 2.
- **Smoothing:** none, and none is expected. The params follow the Chromium timeline (T01's `Param`).

## Fixes made in this review (owned files)

1. **Nyquist clip before detune** (`src/dsp/oscillator.cpp`). Chromium's frequency AudioParam has the nominal range
   ±Nyquist. It clips the timeline value, `FinalValue()` and the input sum before detune multiplies them.
   - Probe at 48 kHz, 30000 Hz, detune −1200: Chromium plays 12000 Hz, and the port played 15000 Hz.
   - This affected k-rate frequency with any detune, and a-rate frequency with a-rate detune.
   - `freq_` cannot carry the range, because the sample rate is unknown at construction, so `process()` clips it.
   - Vectors: `osc-freq-above-nyquist-detune`, `-arate-detune`, `-detune-ramp`, `osc-fm-above-nyquist-detune`.
2. **automationRate** (`src/dsp/oscillator.{h,cpp}`, `// INTERFACE-CHANGE(T11a review)`, additive). It adds
   `setFrequencyRate(Param::Rate)` and `setDetuneRate(Param::Rate)`, both a-rate by default.
   - A k-rate param uses its timeline value at the quantum start plus the **first frame** of the input sum
     (`freqMod[0]` / `detuneMod[0]`), clipped, once per quantum. The vectors confirm this.
   - voice.js:846 sets `o.detune.automationRate = 'k-rate'` and links `bendCS`, vibrato and drift into it (contract
     Q6). Without this, T11 could not match its synth goldens.
   - **T11, T15 and T16 must call `setDetuneRate(Param::Rate::KRate)` wherever the JS sets it.**
   - Vectors: `osc-detune-krate-ramp`, `osc-detune-krate-input`, `osc-detune-krate-timeline-input-subsample`,
     `osc-freq-krate-input`, `osc-detune-arate-input`.
3. The detune input sum is clipped to the detune range (±153600 cents), as Chromium's param clip does. This makes no
   audible difference, because `exp2` saturates either way.
4. `BufferSource::channels()` is clamped to 2 (see Overruns above).
5. Test changes (`tests/test_sources.cpp`):
   - the harness supports `fRate`/`dRate`/`fIn`/`dIn` (ConstantSource inputs into the params);
   - `buf-rate-fast-clamp` is off the silence whitelist;
   - the new above-Nyquist cases cannot hide behind the whitelist;
   - the case floor is raised from 130 to 146.
6. `tools/golden/vectors/dump-sources.mjs` has 9 new cases and the same spec fields. `data/sources.txt` was
   regenerated: 146 cases.

## Open items

| id | severity | item | exact change needed |
|---|---|---|---|
| O1 | low (Q11 FM is statistical) | FM error scales with modulation depth. The modulator's tables differ from Chromium's RustFFT float32 tables by about 2.4e-7 relative, and the carrier integrates that times the depth. Isolated: the carrier fed Chromium's own modulator output is within 2.4e-7, but fed the native modulator at depth 8000 it is 2.0e-5 off over 4096 frames. Depth 2000 gives 9.5e-6. The phase error grows with render length. An exact-tier FM fixture with a depth above about 2 kHz or a long render will miss 1e-5. | Only if T15 needs exact FM: port RustFFT's f32 inverse path (`prepare_inverse_fft_even` plus the half-size complex FFT with RustFFT's planner choice for 1024, 2048 and 8192 points) to make the tables bit-exact. That is a large change and not worth it for Q11. |
| O2 | info | `stop(when < 0)` clamps to 0 and stops at once (`sched::State::stopAt`). The builder's report says negative times are ignored, but that is true only for `start()`. Chromium throws. | None needed, or document it in `oscillator_schedule.h`. |
| O3 | info, T11 | A start time in the past is clamped lazily, on the first `process()`. `process()` must therefore run every quantum while the node is alive. The builder notes this too. | T11/T13: never skip `process()` on a started source. |
| O4 | info | `PeriodicWave` tables are per sample rate. On a rate change the owner must rebuild them (`Service::onRateChanged`). The oscillator's phase is in table samples and is not rescaled, as in Chromium's `SetPeriodicWave`. | T11/T16: rebuild the waves and re-attach on `RateChanged`. |
| O5 | orchestrator | `unit.clock` and `unit.golden-analytic` expectations are stale (T03 lookahead, T07 landed). `rt.realtime` xruns under ASan on a loaded box. | Update `tests/test_clock.cpp` and `tests/test_golden.cpp:116` (orchestrator-owned). |
| O6 | info | `ended` is checked against Chromium in 4 cases only, by quantum. | Optional: more `trackEnd` cases (loop plus stop, duration plus offset). |

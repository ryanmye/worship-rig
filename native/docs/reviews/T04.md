## Fixed in this review (T04-owned files)

   line + tail, and its state was exactly zero". It renders under `rt::RenderScope` and checks three things:
   - the skip starts only after the output has gone to exact zero;

## Open findings

### 1. MEDIUM: the byte cap ignores the running state, so the iPad can exceed its 30 MB reverb budget

`ReverbPool::bytes()` (`src/fx/reverb_service.cpp:90`) counts only pool kernels. Each render slot, including Idle
slots kept for reactivation, also holds a `ConvUnit`: convolver FDL, buffers and predelay lines. That state is about
as large as the kernel. Measured at 48 kHz:

| space | kernel | slot state |
|---|---|---|
| room | 1.50 MB | 2.47 MB |
| hall | 6.37 MB | 7.35 MB |
| wash | 7.75 MB | 8.72 MB |

On the iPad profile (4 units / 32 MB) the worst case is about 31 MB of kernels plus 4 × 8.7 MB of slot state, roughly
66 MB. ARCHITECTURE §7 allows ≤ 30 MB for the iPad reverb. Even one active wash plus one idle wash is 17 MB of state on
top of the kernels.

Change:
- Record `ConvUnit::bytes()` in `SlotMirror`:
  - set it where `swapUnit` / `buildUnit` send `AttachKernel` or call `installInitial`;
  - reset it on `Release` and `dropKernel`.
- Count it in `bytes()`.
- In `evict()`, when over `maxBytes_`, first release the least recently used Idle slots (`ReverbOp::Release`, then
  mirror reset), then drop non-busy kernels.
- Add a test to `test_reverb_engine.cpp`: iPad profile, then alternate the hall, cathedral and wash spaces with
  `commitTo`. Assert that kernels plus slot state stay ≤ `maxBytes()` once the fades have finished.

### 2. MEDIUM (environment contract; no defect on the graph path): the idle skip and the CPU cost depend on FTZ/DAZ

The HPF/LPF recursion holds float values, as Chromium's does. Without flush-to-zero it settles into a denormal limit
cycle: the input never reads as exactly zero, the slot never skips, and the convolvers run on denormals.

Measured with `ReverbUnit` driven directly (one impulse, then 30 s of silence, 48 kHz):

| FP mode | last rendering quantum | cost after 20 s |
|---|---|---|
| FTZ/DAZ (`rt::RenderScope`) | 3.4 s (room), 11.9 s (wash) | 11–12 µs per quantum |
| no FTZ | never stops | 1.46–1.51 ms per quantum, 55 % of the 2667 µs period |

`Graph::renderQuantum` (`src/graph/graph.cpp:332`) opens `RenderScope`, so the engine path is correct. This is not a
T04 code change. It is a contract for T08, T09 and T10, and for any future direct caller of `Unit::process`:

- every render entry must run inside `rt::RenderScope`;
- the Apple render callback and the devhost must reach units only through `rig_render` → `Graph`.

The new test pins the behaviour under FTZ.

### 3. LOW: a fifth overlapping space hard-cuts a fading unit

When the active slot and the other three slots are all Fading, `ReverbPool::pickSlot()`
(`src/fx/reverb_service.cpp:525`) hands the fading slot with the earliest `idleAt` to the new unit. Its tail stops
abruptly. JS keeps every fading unit.

This needs more than three swaps within 0.85 s. That is reachable with back-to-back commits, which are not debounced;
live requests are debounced by 300 ms and cannot reach it alone.

Change: in `swapUnit`, when `pickSlot()` returns a slot whose mirror is `Fading`, defer the swap with
`at(slots_[s].idleAt + 0.001, …)` and the same `seq` check as the "wanted unit still fading" branch. Alternatively,
raise `kReverbSlots` to 6, which costs memory per finding 1.

### 4. LOW (note): `wa::Param` capacity versus equal-power fades

One `equalPowerFade` inserts 33 events (`kCapacity` = 64). A fade that cuts into a running one stays at 48, because
`cancelAndHold` trims. Two non-overlapping fades on the same param that are both still in the future (more than 0.8 s
apart, neither rendered yet) need 66 events, so the second fade is truncated: the gain would stop part-way. The
pool schedules fades at or near now, so this is not reachable today. Keep it in mind if T13 schedules commits far
ahead.

### 5. INFO: `undampedOptIn` is not a reverb test

`undampedOptIn` (`test/phase1/engine/suites.mjs:1844`) tests the sampler's `undampedFrom` field. The builder dropped
it from the T04 list without saying so. Orchestrator: move it from the T04 row of BUILD_PLAN to T12.

## Real-time and port read-through (no defect found)

- **Audio thread** (`ReverbUnit::process` / `apply` / `renderSlot`): no allocation, locks or unbounded loops.
  - Payloads go back through `giveBack`. A 17th replacement within one quantum leaks instead of freeing on the audio
    thread; that is documented and never sent.
  - `pffft` setups are function-local statics, created first on the control or worker side (magic-static guard only
    on the audio thread).
  - Stage MACs are spread so that a quantum does at most one 16384-point FFT or IFFT per channel, with the channels
    staggered. Measured p99.9 ≈ 100 µs.
  - The allocation trap stays clean in the golden test.
- **Convolver**:
  - Overlap-save timing per stage checked by hand: stage 1 plays the next quantum at tap offset B; stages 2 and 3
    compute over the next period and play the one after, at tap offset 2B.
  - The `tailFrames()` bound covers block fill, the FDL residency of both windows holding a sample, the
    accumulator and `ready`.
- **Predelay**: `PredelayLine` matches Chromium's SSE a-rate kernel: write first, then a float read position, then
  `cvttps`, then wrap. The fractional-delay golden (hall) confirms it.
- **IR**: `ir_gen.cpp` was compared line by line with `fx.js` `irGen`, `biquadCoefs` and `reverbBucket`/`dampQ`, and
  matches: JS evaluation order, Float32Array rounding points, draw order including the skipped draws when
  `pos ≥ len`, and `|| 0.01` / `|| 1`.
- **Control logic**: `_swapUnit`, `_pdTo`, `request` and `commitTo` were compared with fx.js 906–1095 and follow
  it: 0.8 s / 0.5 s fades, disconnect 0.85 s after the swap, `pdBusyUntil` + 5 ms pending re-apply, debounce 0.3 s.

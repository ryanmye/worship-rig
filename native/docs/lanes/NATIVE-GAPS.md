Hard rules that apply to every lane:
- GarageBand / Logic conversions are Apple-licensed personal content. The importer writes only into the My Samples home
  (`~/Music/Worship Rig/Samples/`, or the first `RIG_USER_SAMPLES` entry), never into the bundle, `app/` or git. Tests
  use synthetic `.exs` files (`tools/exs/writer.mjs`) and generated audio, never Apple files [R CLAUDE.md "My Samples";
  docs/garageband-import.md:12-25].

  personal content, like My Samples [R CLAUDE.md "Patch packs", "Optional sound packs"].
- Publishing (tags, releases, uploads, pushing `main`) is tier 1. B3 prepares only [R MAC_CHECK.md:375-378].

## 0. Findings that shape the plan

1. **The Song bank needs no app/js change.** `controller.rescanPatchPacks` already accepts the `rig:` protocol and asks
   `./api/health`, then `./api/user-patches` only when health says `userPatches: true` or lists `'user-patches'`
   [R app/js/controller.js:2774-2786]. The native scheme handler hard-codes `userPatches: false` and an empty stub
   [R native/apple/Sources/Shared/RigSchemeHandler.swift:56-68]. Serving real pack JSON from the My Samples roots
   is therefore enough to fill the bank (and the auto-pack top-up). Bank songs that use only factory instruments sound
   at once. Songs that use `user:` samplers need lane N2.
2. **The core is already ready for My Samples and pads.** `rig_config.user_manifest` / `pads_dir` exist, and so does
   `rig_set_paths(e, user_manifest, pads_dir)`, callable from any thread [R native/core/include/rig/rig_engine.h:231-234,
   341-347]. The drone resolves relative pad paths against `pads_dir` [R native/core/src/drone/drone_service.cpp:258-259].
   The bridge sends `path ?? url` [R app/js/engine-bridge/bridge-engine.js:144-157]. The shell passes neither path
   [R RigHost.swift:161-162], and `RigPaths.userSamplesManifest` is nil [R RigPaths.swift:67]. What is missing is a
   merged manifest **with file paths** (server.js rewrites to `/user-samples/<token>/…` URLs, which the core cannot read
   [R server.js:293-337]), plus the pad folder.
3. **`isElectron` is a poor switch for the native shell.** It gates 43 sites in 8 files [R grep]. Setting it to true on
   the Mac would break the shell: `installShellHook` *replaces* `window.__rigShell` [R controller.js:3790-3796], which
   holds the native menu dispatcher and the first-launch `menuReady` probe [R RigLibrary.swift:189-194, 266-273], and
   stop() deletes it [R controller.js:3984]. Other effects would be "Electron" rows in About, the Electron MIDI texts and
   `checkOtherLibrary`. So lane N0 adds a capability flag (`rig.shell === 'native'`) and moves the Mac-only gates to
   it, or to member presence. This also fixes LaneR O1 and the wrong Chrome text in About and Library & Backup
   [R views/settings.js:1508-1535, 1782-1801; views/v6/settings.js:401-404].
4. **The `window.rig` polyfill is a Swift string** [R RigLibrary.swift:186-217]. Every lane below adds members to it.
   Lane N0 moves it into real JS files that are injected in a fixed order, with one Swift handler per feature. Then
   each lane adds its own file (no merge hotspot), and node tests can run the same JS against a fake
   `webkit.messageHandlers.rigShell`. This follows the pattern test/unit/selftest already uses: JS lifted from Swift
   and run in node [R test/unit/selftest/selftest-scripts.test.mjs:12-23].
5. **Swift is compiled only by CI's `mac-check`** (macos-15: `check.sh --stage tools,apple-mac,apple-sim`, then
   `selftest`) [R .github/workflows/native-core.yml:151-188]. Lanes don't push, so a Swift compile error shows up only
   after the orchestrator pushes. Two consequences:
   - Keep the Swift thin. Put logic in C++ (ctest on this box) or JS (node:test and Playwright on this box).
   - Every lane adds a self-test step (`RigSelfTest.swift`, run headless on the CI Mac) for whatever can run without a
     person.
6. **Testing on Linux through `rig-devhost`.** devhost is RigHost in miniature over WebSocket and already stubs the
   same `/api/*` routes [R native/devhost/src/devhost.cpp:132-137]. If the pack and sample scanners live in a small C++
   library that both the Swift scheme handler and devhost call, Chrome + devhost runs the real scanner, the real core
   and the real UI on Linux (Song bank, a `user:` sampler sounding on the null backend).
7. **The pure parts of the GarageBand importer can be reused as they are.** `tools/exs/parser.mjs`, `layout.mjs`,
   `mapping.mjs` and `wav.mjs` import nothing from node [R grep `^import` tools/exs]. The parser was checked byte by
   byte against real Apple files on Ryan's Mac [R docs/garageband-import.md:190-197]. Porting it to Swift or C++ would
   throw that verification away. Only the fs orchestration and the audio conversion are Node- or ffmpeg-bound
   [R tools/exs/importer.mjs:7-15, convert.mjs:13-17].
8. **B2 is worse than "nothing saved".** `decidePolicyFor` answers `.allow` for `blob:` and `data:`
   [R RigNavigation.swift:36]. An `<a download>` on a `blob:` URL may therefore navigate the app's only web view to the
   JSON, replacing the UI while the core keeps playing [U, per WEBKIT_AUDIT §1 "Downloads"]. Both download helpers
   revoke the URL after 10 s [R views/settings.js:228-236; views/edit/lib.js:200-209], which a slow save panel can
   outlast [U].
9. **Hidden-window throttling.** 1.x sets `backgroundThrottling: false` [R main.js:1427]. Menu-bar mode needs the
   hidden main page (controller, bus, watchdog) to keep running. `WKPreferences.inactiveSchedulingPolicy = .none`
   (macOS 14 / iOS 17 SDK, inside the 14.5 floor) is the public switch [E; behaviour U].

## 2. Lane plan

Every lane has a builder and a skeptic, follows RESUMABLE.md (commit early, `LANE.md`, `gates.mjs`), ships alone,
needs no flag (each feature is gated on the existence of its `window.rig` member or route, as the app already does),
adds its rows to `docs/release-notes-2.0.md` "Known gaps" (removes them), updates the user doc it touches
(patch-packs.md "Where it works", garageband-import.md "In the Mac app", menubar-mode.md, README), logs interface
changes in CONTRACT_CHANGES, and adds its Mac / iPad checks to MAC_CHECK step 4 / step 5. "Linux" below means this box
(node:test, Playwright Chromium, ctest g++ / clang++-20 -Werror, devhost null backend). "CI Mac" means the
`mac-check` job after the orchestrator pushes (compile plus the headless self-test).

### Order and dependencies

```
wave 1:  N1 Song bank (packs)  ‖  N0 shell surface  ‖  N10 B3 release (yaml/scripts only)
wave 2:  N2 My Samples sound (N1, N0)  ‖  N3 B2 files (N0)  ‖  N5 menus, window, keep-awake (N0)
wave 3:  N4 My Pads (N0, N1)  ‖  N8 global shortcuts (N0)  ‖  N9 update check (N0, N10 names)
wave 4:  N6 GarageBand importer (N2)  ‖  N7 menu-bar mode + login item (N5)
```

N1 goes first and needs nothing: it only changes the scheme handler and adds hostkit, so the Song bank fills before
any app/js work. N0 runs in parallel because every other lane builds on its polyfill layout. Because of the 2-CPU
box, run at most two heavy lanes at once (gates one at a time through `gates.mjs`). N10 is light (yaml and docs).

Total [E]: N1 2.0 + N0 1.5 + N10 1.0 + N2 2.0 + N3 1.5 + N5 1.5 + N4 1.5 + N8 1.5 + N9 1.0 + N6 5.0 + N7 3.0 =
**21.5 agent-days**, above D35's 12–20 [E]. The importer and menu-bar mode are most of the difference.
